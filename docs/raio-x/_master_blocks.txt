### CONFLITOS (resoluções)

1. **P014, P015** — Mesmo código (marcar-item desmarcar / estornarLiberacaoReserva). P014 quer desfazimento tudo-ou-nada (RPC com RAISE em qualquer falha → rollback total). P015 quer estorno TOLERANTE (clampar R ao saldo livre + status_alerta) porque a nota de P015 contraria o ledger imutável e respeita_nota=false. Colidem: all-or-nothing estrito vs degradação tolerada no mesmo ponto de estorno-L.
   → *Resolução:* Implementar UMA RPC wms_desmarcar_item_atomico onde a transação é atômica (P014) MAS o estorno-L usa o caminho tolerante: se recriar a R full violaria a CHECK, recria clampada ao saldo livre e seta status_alerta DENTRO da mesma transação (não falha o desmarque). Confirmar com o user que P015 diverge da letra da nota (estratégia técnica fiel ao ledger vence). Um PR único na fase 5.

2. **P056, P060, P061** — Inventário aplicar (P060) e estornar (P056/P061) tudo-ou-nada compartilham helpers plpgsql de 'lote de contra-movs com preflight'. P061 é o mesmo código de P056 (deps).
   → *Resolução:* Uma migration com 2 RPCs (wms_aplicar_sessao_inventario, wms_estornar_sessao_inventario) compartilhando o helper de preflight. P056+P061 no mesmo PR (fase 4); P060 na fase 5 (maior blast). P061 effort S porque o trabalho é P056.

3. **P099, P109** — Mesma primitiva e migration (dedup de recebimento por assinatura NF). P109 deps P099.
   → *Resolução:* Um índice único parcial + captura de 23505 na RPC cobre os dois. Mesmo PR na fase 2.

4. **P108, P104** — Ambos 'custo zero na entrada'. P108 bloqueia no RPC (hard); P104 quer fallback de custo médio nos routes de entrada (não bloquear cego). Risco de dupla-regra conflitante.
   → *Resolução:* P108 (RPC) é a rede de segurança terminal: bloqueia/aplica custo mínimo SÓ nas origens que recalculam custo. P104 (routes) faz fallback de custo médio histórico ANTES de chamar a RPC. Fazer P108 primeiro (fase 2), P104 depois (fase 6). Não duplicar a lógica de custo médio.

5. **P108, P110** — Ambos tocam o corpo de wms_inserir_movimentacao (guard de custo-zero + reversão de custo médio no estorno). Duas redefinições da RPC colidiriam.
   → *Resolução:* Unir numa migration só que recria wms_inserir_movimentacao com os dois guards (custo-zero + reversão no estorno). Fase 2, PR único.

6. **P124, P125** — P125 deps P124 (mesma migration UNIQUE serve de backstop de banco). Mesmo arquivo de rota.
   → *Resolução:* Migration do P124 cobre o backstop de banco do P125. P124 primeiro; P125 adiciona só o disabled no botão. Mesmo PR fase 2.

7. **P138, P139** — Mesma rota e mesma RPC wms_set_role_permissoes. P139 (lock concorrente) sai de graça com SELECT FOR UPDATE da row do role dentro da RPC de P138.
   → *Resolução:* PR único: a RPC faz FOR UPDATE da row do role (serializa P139) + delete+insert atômico (P138). Nota pede '2º admin vê aviso e espera' → avaliar advisory NOWAIT→409 vs blocking. Fase 1.

8. **P049, P050, P051, P052, P054** — Devoluções: P049/P050 atomicidade movs+status, P052 claim concorrente, P051 preflight quarentena (muda o fluxo da Classe B), P054 lock pessimista. Tudo no mesmo classificarDevolucao. P051 precede (deps de P049).
