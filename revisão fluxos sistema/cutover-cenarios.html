Cutover de reservas — Todos os cenários após o deploy

Como cada caminho do sistema vai se comportar depois que a refatoração do cutover R→L+S estiver em produção. Cobre 14 cenários, do feliz ao patológico.

Os princípios da nova arquitetura

A regra invariante:

O cutover R→L+S dispara quando, e somente quando:
status_separacao ∈ {separado, embalado, expedido}  E  nota_fiscal_id IS NOT NULL  E  estoque_lancado = false.

Quem chegar por último no encontro de "status forward" + "NF existente" dispara. Quem sair desse conjunto com estoque_lancado=true reverte.

Cenário 1 — Pedido normal (caminho feliz) 95% dos pedidos

A situação

Pedido: 5 unidades de PEC-001. NetAir CWB. Rota: própria. NF emite na aprovação, operador separa fisicamente, conclui.

Sequência de eventos

T+0s — webhook do pedido
Sistema cria R de 5un. Status: aguardando_aprovacao.
T+30s — aprovação automática
Enfileira lancar_estoque. Worker gera NF stub, salva nota_fiscal_id. Status: aguardando_separacao.
Cutover NÃO dispara porque status não está no conjunto forward.
T+10min — operador inicia separação
Status: em_separacao. Bipa cada item. Saldo intacto, reserva intacta.
T+15min — operador conclui
Endpoint /separacao/concluir muda status pra separado. Chama dispararCutoverSePronto: status forward + NF existe → enfileira pos_nf. Worker emite L+S, marca estoque_lancado=true.
T+16min — embalagem
Operador embala. Status: embalado. dispararCutoverSePronto chamado de novo (idempotente — pula porque estoque_lancado=true).
T+20min — expedição
Status: expedido. Mesma idempotência protege.

Cenário 2 — Concluir-OC puro NF gera depois do separado

A situação

Pedido OC: 3 unidades de PEC-002. Aguardando validação dos itens (encontrei/esgotado). Operador valida tudo como "encontrei". Pedido pula direto pra separado SEM ter tido NF antes.

Sequência

T+0 — pedido OC entrou
Itens marcados como compra_status='oc_pendente'. Status: aguardando_compra. Sem reserva ainda (OC não reserva — peça nem está na prateleira da empresa).
T+1h — compra chegou, foi recebida
Estoque entra (E) na empresa de origem.
T+1h05 — operador valida
Endpoint /separacao/concluir-oc muda status pra separado + enfileira lancar_estoque.
Chama dispararCutoverSePronto: status forward ✓, mas NF AINDA NÃO existe → skip (loga "aguardando NF").
T+1h05 + 3s — worker processa lancar_estoque
Gera NF, salva nota_fiscal_id. Worker chama dispararCutoverSePronto no final: status já é separado + NF agora existe → enfileira pos_nf. Worker emite R implícita + L + S.
O detalhe: nesse fluxo, a R nasce e morre quase ao mesmo tempo. Tecnicamente o RPC wms_inserir_movimentacao exige uma R antes de uma L. O executarEstoquePosNfWms cria a R no momento e em seguida converte. Conceito: a peça já está na prateleira (recebida) e está saindo agora.

Cenário 3 — OC com compra mix Parcial → separação normal

A situação

Pedido: 3 itens diferentes. 2 itens têm estoque (vira R normal). 1 item precisa comprar (vai pra OC, sem reserva). Pedido fica aguardando_compra.

Sequência

T+0 — pedido entra
2 reservas R criadas pros itens disponíveis. 3º item: aguardando OC.
T+1d — compra do 3º item chega
compras-release entra: gera NF (item 3 + os 2 anteriores), muda pedido pra aguardando_separacao, enfileira lancar_estoque.
T+1d + 2s — worker gera NF
dispararCutoverSePronto chamado: status ainda é aguardando_separacao (não forward) → skip.
T+1d + 5min — operador bipa todos
Bipa os 2 originais + 1 da compra. Concluir → separado. dispararCutoverSePronto: forward + NF → cutover dispara pros 2 itens originais. Item 3 também sai (R nasce-e-morre como no cenário 2).
Resultado: o pedido mistura R "viva por dias" (itens originais) com R "instantânea" (item OC). O cutover trata todas as reservas do pedido de uma vez — não importa quando nasceram.

Cenário 4 — Embalagem direta OC (skip separado) Status pula etapa

A situação

Pedido OC pequeno: operador resolve embalar direto sem passar pela tela de separação. Vai em "embalagem", bipa itens (via /bipar-embalagem-oc ou /confirmar-item-embalagem) e o status pula de aguardando_compra direto pra embalado.

Sequência

T+0 — pedido OC após compra recebida
Status: aguardando_compra. Sem reservas (OC não reserva).
T+1min — operador bipa último item em embalagem
Endpoint detecta pedido completo, muda status pra embalado + enfileira lancar_estoque.
Chama dispararCutoverSePronto: status forward ✓, NF ainda não → skip.
T+1min + 2s — worker gera NF
Worker chama dispararCutoverSePronto: status embalado (está no conjunto!) + NF agora existe → enfileira pos_nf. Cutover acontece.
T+1min + 3s — etiqueta imprime
Em paralelo, imprimirEtiquetaDireta roda. ZPL já cacheado ou baixado.
Por que isso funciona: o conjunto forward é {separado, embalado, expedido} — não exige passar por separado especificamente. Qualquer um dos três satisfaz a regra. O fluxo OC direto pode "pular" separado sem quebrar a invariante.
Resultado: o pedido finaliza fisicamente (operador embalou) e o ledger se ajusta em segundos. Etiqueta imprime independente do cutover (eventos paralelos). Cycle count consistente.

Cenário 5 — Desfazer-bip pós-embalado Reversal automática

A situação

Pedido já embalado: operador percebe que bipou item errado, usa /desfazer-bip. Status reverte de embalado pra em_separacao. Mas o cutover JÁ FOI: existe S no ledger.

Sequência

T+0 — pedido em embalado
Cutover já rodou. Saldo baixou. estoque_lancado=true.
T+5min — operador desfaz bip
Endpoint detecta retrocesso de status. Chama reverterCutoverSeRetrocedeu antes de mudar status:
  1. Lê movimentações S do pedido
  2. Cria E compensatória pra cada S (com estorno_de=S.id)
  3. Lê movimentações R originais (já liberadas mas no ledger)
  4. Cria nova R na mesma quádrupla, com novo TTL de 30d
  5. Marca estoque_lancado=false
Depois muda status pra em_separacao.

Cenário 6 — Admin voltar-etapa backward Reset profundo

A situação

Pedido em expedido: descobriu-se erro grave (etiqueta errada, destinatário trocado). Admin usa /separacao/voltar-etapa pra mover de expedido direto pra aguardando_separacao.

Sequência

T+0 — pedido em expedido
Cutover rodou há tempos. estoque_lancado=true. Etiqueta impressa.
T+1h — admin executa voltar-etapa
Endpoint detecta retrocesso GRANDE (3 níveis pra trás). Chama reverterCutoverSeRetrocedeu: estorna S, recria R. Marca estoque_lancado=false. Limpa separacao_iniciada_em, separacao_concluida_em, embalagem_concluida_em. Status: aguardando_separacao.
T+1h + 1s — fluxo retoma
Pedido volta pra fila do operador. NF continua existente (não cancela NF fiscal). Etiqueta pode ser reimpressa.
NF não é cancelada automaticamente. Voltar-etapa é operação de processo interno — o "papel da NF" continua válido fiscalmente. Se a NF realmente precisa ser cancelada, é fluxo separado (cancel webhook do Tiny).
Resultado: reset profundo controlado por admin. Ledger conta a história inteira: R→L→S→E→R'. Cinco linhas de auditoria.

Cenário 7 — Encaminhar antes do cutover Caminho leve

A situação

Pedido em aguardando_separacao: CWB descobre que não vai conseguir despachar a tempo. Pede pra SP separar. Cutover ainda não rodou (status não é forward).

Sequência

T+0 — operador clica encaminhar pra SP
Endpoint /separacao/encaminhar chama:
  1. liberarReserva({motivo: 'encaminhamento'}): cria L pra cada R em CWB
  2. recriarReservasNoGalpao({galpao_destino: SP}): procura saldo em SP, cria R nova
  3. Reseta pedido pra pendente com sugestão="transferencia"
NF preservada. Etiqueta limpa pra reprintar.
Por que não chama reverterCutoverSeRetrocedeu? Porque estoque_lancado=false — não tem S pra estornar. O encaminhar já usa diretamente os helpers de baixo nível (liberarReserva + recriarReservasNoGalpao). A função de reversal só age se houver cutover pra desfazer.

Cenário 8 — Cancel antes do cutover Só libera R

A situação

Pedido em aguardando_separacao: cliente cancelou no marketplace. Webhook de cancelamento chega do Tiny. estoque_lancado=false, então só tem R pra liberar.

Sequência

T+0 — webhook cancel chega
Webhook handler vê codigoSituacao='cancelado'. Como existingOrder.estoque_lancado=false:
→ chama liberarReserva({motivo: 'cancelamento'})
→ cria L pra cada R ativa
→ marca pedido status='cancelado', status_separacao=null
Resultado: 1 R + 1 L no ledger. Saldo intacto. Disponível volta. Outro pedido pode pegar esse estoque imediatamente.

Cenário 9 — Cancel depois do cutover Estorna S + alerta

A situação

Pedido em embalado: cliente cancelou tarde (raro mas acontece — chargeback, fraude). Cutover já rodou. Existe S no ledger.

Sequência

T+0 — webhook cancel chega
Como existingOrder.estoque_lancado=true:
→ chama estornarSaidasPedido({motivo: 'cancelamento'})
→ cria E compensatória pra cada S existente
→ marca compra_estoque_lancado_alerta=true no pedido
→ marca status='cancelado'
Diferença importante: NÃO recria R. Cancelar é diferente de "voltar etapa". Quando cancela, o pedido morre. Estoque volta pra "disponível geral" — qualquer outro pedido pode pegar. Não tem reserva pra recriar.

A bandeira compra_estoque_lancado_alerta avisa o operador: "estoque foi 'desfaturado' — verifique se a NF foi cancelada fiscalmente no Tiny."

Cenário 10 — NF webhook chegando tarde Race entre concluir e webhook

A situação

Pedido com NF demorada: em modo Tiny→WMS migrado, a NF do Tiny demora minutos pra autorizar. O operador é rápido — bipa tudo e termina ANTES do webhook da NF chegar. nota_fiscal_id=null no momento do concluir.

Sequência

T+0 — operador conclui antes da NF
Status: separado. dispararCutoverSePronto chamado: forward ✓, mas NF ausente → skip + loga "aguardando NF".
T+30s — NF webhook chega
nf-webhook-handler salva nota_fiscal_id. Em modo WMS, NÃO enfileira pos_nf direto (refatoração removeu isso). Em vez disso, chama dispararCutoverSePronto no final: status é separado ✓, NF agora existe ✓ → enfileira pos_nf. Cutover dispara.
Simetria perfeita: tanto faz a ordem em que os eventos chegam — quem completar a interseção dispara. Nenhum evento "perde a janela".
Resultado: race condition tratado naturalmente pela arquitetura. Sem locks complexos, sem semáforos. A invariante é a verdade — verificar a invariante em cada ponto de chamada resolve.

Cenário 12 — Reserva expirando (TTL 30 dias) Cleanup automático

A situação

Pedido travado: chegou há 32 dias, NF emitida, ficou em aguardando_separacao. Ninguém separou (perdeu de vista, sumiu da fila visual). Cron de cleanup roda às 3h AM.

Sequência

T+0 — pedido entrou há 32 dias
R criada com expira_em = pedido + 30d. Hoje já expirou há 2 dias.
T+32d, 3:00 AM — cron dispara
Endpoint /api/wms/reservas/cleanup chamado pelo Vercel cron. Função cleanupReservasExpiradas:
  1. Busca R com expira_em < now()
  2. Pra cada uma: checa se já tem L apontando (pula se sim)
  3. Cria L com motivo "expirado"
  4. Marca pedido status_alerta='reserva_expirada'
T+32d, manhã — operador entra
Vê pedido com alerta visual vermelho. Sabe que precisa investigar: a NF ainda existe no Tiny, mas a reserva sumiu. Decide: cancelar fiscalmente ou criar nova R via admin.
Importante: uma reserva expirando significa que o sistema "abriu mão" do estoque depois de 30 dias sem ação. É sintoma de problema operacional — pedido foi esquecido. O cleanup é a rede de segurança final pra impedir vazamento de reserva indefinidamente. Nunca deveria acontecer em operação saudável.
Resultado: estoque é liberado pra outros pedidos. Pedido fica com alerta. NF fiscal continua existindo no Tiny (precisa ser tratada manualmente se for cancelar).

Cenário 13 — Race: 2 operadores concluindo o mesmo pedido CAS atômico

A situação

Pedido em em_separacao: 2 operadores em terminais diferentes terminam de bipar tudo ao mesmo tempo. Ambos clicam "concluir" no mesmo instante. Ambas requisições chegam no servidor em paralelo.

Sequência

T+0ms — operador A clica concluir
Endpoint executa UPDATE siso_pedidos SET status_separacao='separado' WHERE id=X AND status_separacao='em_separacao'. SUCCESS (1 linha atualizada).
T+0ms — operador B clica concluir
Mesma query, mesma condição. Mas o estado já é "separado" agora. 0 linhas atualizadas — o CAS protegeu.
T+50ms — A continua, B retorna pendente
A: dispararCutoverSePronto enfileira pos_nf.
B: pedido aparece em pendentes no response → frontend mostra "já foi concluído".
Mesmo se B tentasse chamar dispararCutoverSePronto também, seria idempotente — o worker checa estoque_lancado e pula.
Defesa em camadas:
  1. CAS no UPDATE — só um operador "ganha" a transição de status
  2. Idempotência via estoque_lancado — pos_nf duplicado vira no-op
  3. Idempotência via estorno_de — mesmo se 2 jobs pos_nf rodarem, cada R só vira L+S uma vez
Resultado: uma só conversão R→L+S. Ledger íntegro. Frontend do operador B mostra mensagem clara ("já concluído por outro"). Sem corrupção, sem duplicação.

Cenário 14 — Falha no worker no meio do cutover Retry seguro

A situação

Pedido com 3 itens: worker processa o pos_nf, converte item 1 (cria L+S), converte item 2 (cria L+S), e no item 3 o banco timeout. Worker lança erro. Job fica em siso_fila_execucao com tentativas incrementado.

Sequência

T+0 — primeira tentativa
Worker pega job. Loop itera reservas:
  • R1 → cria L1+S1 ✓
  • R2 → cria L2+S2 ✓
  • R3 → timeout
Worker joga exceção. NÃO marca estoque_lancado=true (só marca se TODAS converterem).
T+30s — backoff exponencial dispara retry
Worker pega o job de novo. Loop itera reservas:
  • R1 → checa se tem L apontando pra R1 (estorno_de=R1.id): SIM → pula
  • R2 → checa se tem L: SIM → pula
  • R3 → checa: NÃO → tenta criar L3+S3 ✓
Marca estoque_lancado=true.

Pontos onde a invariante é aplicada

Toda transição de status na separação chama um dos 2 helpers:
  • dispararCutoverSePronto em: concluir, concluir-oc, confirmar-item-embalagem, bipar-embalagem-oc, voltar-etapa (forward), retry-etiqueta, nf-webhook-handler, execution-worker (após NF)
  • reverterCutoverSeRetrocedeu em: desfazer-bip, voltar-etapa (backward)
Os helpers checam a invariante e fazem ou não fazem. Chamar onde não precisa é seguro (no-op por idempotência).
