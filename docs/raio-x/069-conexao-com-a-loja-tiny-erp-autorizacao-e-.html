Conexão com a loja (Tiny ERP) - autorização e avisos de pedidos

Quando um pedido entra na loja (Tiny avisa o sistema), o sistema é autorizado pra acessar o estoque de Tiny e dar baixa. Essa é a "ponte" entre a loja e seu WMS.

O que já funciona

  • ✓Autorização segura: sistema pede permissão antes de tocar no estoque — ninguém consegue acessar sem autorizar
  • ✓Chave de acesso renovável: quando a permissão vence, sistema renova automaticamente — não fica bloqueado
  • ✓Aviso de pedido duplicado é evitado: se Tiny enviar o mesmo pedido 2 vezes por engano, sistema processa só uma vez
  • ✓Nota fiscal é tratada separada: quando nota fiscal chega (devolução ou saída oficial), sistema sabe diferenciar de pedido normal

Problemas pra resolver · 3

P091Galpão muda no meio do caminho — estoque fica em lugar errado

graveIntegração com a loja (Tiny / marketplace)

Imagina assim: Pedido P123 chega com galpão CWB. Sistema separa 500 peças de lá. Admin muda o galpão pra Vault. Sistema tenta guardar no Tiny em Vault, mas as peças estão em CWB.

Hoje: 1) Pedido P123 chega com depósito 100 (CWB). Sistema aprova: 500 peças encontradas, envia pra separação. 2) Admin muda a configuração pra depósito 200 (Vault). 3) Sistema tenta atualizar o Tiny dizendo que guardou em Vault. Mas as peças estão em CWB — Tiny fica confuso.

Por que importa: Quando o cliente pede rastreamento ou fazer reposição futura, o Tiny diz que tem 500 peças em Vault mas elas nunca chegaram lá. Inventário fica inconsistente.

Gravar no pedido QUAL galpão foi escolhido no momento da rota, não deixar mudar depois

  • Bloquear mudança de galpão depois que pedido já roteou — Pedido fica vinculado ao galpão original. Não resolve problema se admin mudar ANTES de processar, só após.
  • Salvar galpão no pedido (na criação ou rota). Sistema usa esse galpão pra sempre. — Mesmo que admin mude a config geral, esse pedido segue o galpão gravado. Consistente até o fim.
  • Deixar como está (dinâmico) — Continua com risco de inconsistência entre loja e galpão.

Recomendo: Opção 2: salvar galpão no pedido na hora que roteia. Faz a lógica simples e imune a mudanças administrativas.

src/app/api/wms/tiny/stock/ajustar/route.ts:108-115 (lê deposito_id dinamicamente de siso_tiny_connections, nao do pedido)

P092Pedido cancelado mas saldo não volta na loja

graveIntegração com a loja (Tiny / marketplace)

Imagina assim: Pedido de 300 unidades é separado e marcado como guardado no Tiny. Depois é cancelado. Sistema devolve as 300 pra prateleira interna, mas Tiny continua achando que tem 300 menos.

Hoje: 1) Pedido chega com 300 unidades. Sistema marca: estoque apartado no Tiny. 2) Pedido é cancelado (loja envia aviso). 3) Sistema libera as 300 peças pro estoque interno. 4) MAS Tiny continua mostrando 300 a menos — nunca recebeu ordem de devolver.

Por que importa: Saldo em Tiny fica permanentemente baixo. Loja oferece produto que na verdade não tem. Clientes pedem produtos indisponíveis.

Quando cancela pedido, se estoque foi lançado em Tiny, deve enviar cancelamento pra loja também

  • Hoje: libera só internamente. Deixar como está. — Tiny continua com saldo errado. Problema persiste.
  • Ao cancelar, chamar Tiny pra estornar as 300 peças — Saldo em Tiny volta ao normal. Loja oferece quantidade certa.
  • Admin entra manual em Tiny pra corrigir cada cancelamento — Funciona mas é manual e propenso a erro.

Recomendo: Opção 2: automático. Quando cancela, sistema avisa Tiny pra devolver os mesmos itens.

src/app/api/wms/webhook/tiny/route.ts:191-245 (libera reservas locais mas não estorna em Tiny)

P093Galpão não tem código — sistema não sabe onde guardar

graveIntegração com a loja (Tiny / marketplace)

Imagina assim: Admin configura conexão com Tiny mas esquece de escolher qual galpão usar (Tiny deixa em branco ou vazio).

Hoje: 1) Pedido chega pra processar. 2) Sistema procura: qual galpão usar? Acha vazio. 3) Manda pro Tiny sem especificar galpão. 4) Tiny usa o primeiro da lista (ninguém sabe qual é). 5) Pode ser que use o errado.

Por que importa: Estoque é contado em galpão aleatório. Pode esvaziar prateleira errada ou deixar stock em lugar inacessível.

Bloquear operação até admin escolher galpão, ou validar no sistema

  • A tela não deixa salvar config sem galpão selecionado — Config incompleta fica impossível. Admin é obrigado a completar.
  • O sistema por tras rejeita pedido com erro se galpão não tiver sido configurado — Admin vê erro, completa a config. Pedido processa depois.
  • Deixa dinâmico, a tela cuida — Se a tela buggar ou alguém editar direto na base, risco continua.

Recomendo: Opção 1 + 2: a tela não deixa vazio, AND o sistema por tras valida. Dupla segurança.

src/app/api/wms/tiny/stock/ajustar/route.ts:143-151 (usa depositos[0] se deposito_id=null, pode ser wrong warehouse)

D051Se a loja fica offline ou bloqueia a gente, quanto tempo o sistema tenta sozinho?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: O sistema tenta atualizar a loja, loja retorna 'acesso negado' ou está fora do ar.

Hoje o sistema: Sistema tenta, loja nega. Erro é registrado como crítico. Sistema aguarda, depois tenta de novo (número de vezes?). Vai ficar tentando sozinho até ser feliz ou até alguém perceber e desligar a conexão manual.

Por que importa: Se deixar tentando infinito, pode ocupar recurso ou ficar fazendo barulho nos logs. Se parar muito cedo, pedidos ficam presos. Precisa de estratégia.

  • Tentar 3 vezes com espera crescente (1min, 5min, 15min), depois avisar admin — Problema transitório é resolvido. Problema crônico o admin descobre rápido.
  • Tentar indefinidamente até sucesso — Pedidos nunca ficam presos, mas pode ocupar sistema se problema for crônico.
  • Tentar 1 vez, se falhar marca pedido como 'erro manual' — admin resolve depois — Simples mas pedidos ficam presos facilmente. Manual demais.

Recomendo: Opção 1: 3 tentativas com espera crescente, depois alerta. Admin vê no painel 'Conexão com loja caiu'.

src/lib/tiny-oauth.ts:149-165 (trata erro, loga como 'critical' mas não resgata job)

D052Empresa tem 2 galpões em cidades diferentes — loja tem depósito de cada um. Conseguimos ligar os 2?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: NetAir: 1 galpão em Curitiba (depósito 100 na loja), 1 em São Paulo (depósito 200 na loja). Sistema hoje: 1 conexão = 1 depósito.

Hoje o sistema: Cada empresa tem 1 conexão loja com 1 depósito associado. Se NetAir tiver 2 galpões, só consegue trabalhar com 1.

Por que importa: Se precisa usar os 2 galpões, tem que escolher qual. Estoque do outro fica invisível pro sistema. Pode perder stock ou oferecer produtos que não estão lá.

  • Criar 2 conexões loja, uma por galpão — Cada galpão trabalha independente. Simples. Mas admin tem que manter 2 tokens/configs.
  • Conectar 1 empresa a N depósitos (quebrar relação 1:1) — Complexo. Sistema precisa saber qual galpão pra qual depósito. Novo campo na config.
  • Deixar como está — empresa escolhe qual galpão usa — Simples. Outro galpão fica de fora.

Recomendo: Opção 1 por enquanto: se NetAir quer 2 galpões, admin cria 2 conexões. Mais trabalho mas desacopla galpões. Opção 2 é futura se virar padrão.

docs/database-schema.md:1144-1170 (1 row per empresa, not per galpao)

D053Alguém roubou a senha da loja — precisa fazer login de novo. Tudo que estava em andamento perde o acesso?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: Admin configura acesso via autorização. Sistema guarda chave de acesso. Depois, admin revoga chave na loja por segurança ou expira naturalmente.

Hoje o sistema: Sistema tenta usar chave expirada. Loja nega. Sistema tenta renovar (usar chave de renovação). Se chave de renovação também expirou, retorna erro. Sistema loga como crítico.

Por que importa: Sem saber se é 'temporário' (chave expirou, basta rodar login de novo) ou 'permanente' (senha mudou, acesso revogado), admin não sabe o que fazer. Pode deixar parado esperando acesso voltar.

  • Diferenciar: se erro é de credencial (chave ruim), mostrar 'Conexão expirada — faça login de novo'. Se é de loja offline, mostrar 'Loja offline — tenta depois'. — Admin sabe exatamente o que fazer. Pode ir no menu Configurações e clicar 'Autorizar de novo'.
  • Deixar como está — sempre erro crítico — Admin tenta de tudo. Confusão.
  • Tentar renovar automaticamente escondido — Problema resolve sozinho se chave renovar. Mas admin nunca avisa se problema é crônico.

Recomendo: Opção 1: painel mostra diferente se é 'autorizar novamente' vs. 'loja offline'.

src/lib/tiny-oauth.ts:149-165 (nao diferencia tipos de erro de refresh)

D054Loja envia aviso de mudança mas com ID vazio ou errado — sistema cancela em silêncio?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: Loja envia aviso de cancelamento mas o campo 'ID do pedido' vem vazio ou em branco.

Hoje o sistema: Sistema checa se ID é válido. Se for vazio, rejeita (retorna erro 400). Aviso nunca é registrado em log. Silêncio.

Por que importa: Admin nunca vê que loja tentou avisar algo. Pode ficar horas procurando por quê pedido não foi cancelado (porque aviso foi perdido).

  • Mesmo que rejeitar, registrar em log: 'Aviso da loja chegou com ID vazio — ignorado' — Admin tem rastreabilidade. Sabe que loja tentou algo mas dados vinham errados.
  • Deixar como está — silêncio — Ninguém sabe que tentou. Debugging fica difícil.
  • Alertar admin por e-mail cada vez que isso acontece — Admin avisa loja que algo tá errado no envio deles.

Recomendo: Opção 1: sempre registrar tentativa (mesmo que rejeitada). Log fica completo.

src/app/api/wms/webhook/tiny/route.ts:134-137 (não insere log se pedidoId vazio)

D055Loja tenta avisar de pedido novo mas sistema ainda não foi configurado — o que acontece?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: NetAir acabou de instalar loja nova. Loja já começa a enviar avisos de pedido. Sistema recebe aviso mas conexão ainda não tá pronta (chave não foi gerada).

Hoje o sistema: Sistema recebe aviso assincronamente (não espera resposta). Processa em segundo plano. Tenta buscar chave — não acha. Log de erro. Aviso é perdido ou fica marcado como erro.

Por que importa: Primeiros pedidos podem ser perdidos. Cliente paga mas pedido não entra no sistema pra processar.

  • Gravar aviso como pendente se chave não estiver pronta. Tentar de novo a cada 5 minutos. — Quando admin habilitar a conexão, sistema processa avisos antigos também.
  • Deixar como está — pedido é perdido, admin precisa avisar cliente — Simples mas acarreta suporte manual.
  • Avisar à loja: 'Tá offline, manda de novo depois' — Loja retem aviso e envia depois. Mas loja pode não fazer isso.

Recomendo: Opção 1: implementar fila de retry. Aviso fica pendente até conexão estar pronta.

src/app/api/wms/webhook/tiny/route.ts:375-396 (fire-and-forget, erro é logged mas 200 já foi enviado)

D056Operador cancela pedido via sistema (não é aviso da loja) — estoque volta na loja também?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: Pedido de 100 unidades foi separado e estoque foi atualizado na loja. Operador depois clica 'Cancelar' no painel interno.

Hoje o sistema: Sistema libera as 100 peças internamente. Mas não confirmei se avisa a loja pra devolver.

Por que importa: Se a loja não recebe aviso, acha que aquelas 100 peças foram entregues. Faz reposição errada ou oferece produto indisponível.

  • Cancelamento manual = cancela só internamente. Admin cancela manual na loja se precisar. — Simples. Mais manual mas control total.
  • Cancelamento manual = avisa a loja automaticamente (como aviso faz) — Sincronizado. Uma ação = dois sistemas atualizados.
  • Não deixar cancelar manualmente se estoque já foi lançado na loja — Força admin a desfazer na loja primeiro. Mais seguro mas engessado.

Recomendo: Opção 2: manual cancela como aviso. Mesmo comportamento em qualquer origem.

src/app/api/wms/webhook/tiny/route.ts:191-245 (webhook faz estorno mas rota manual?)

D057Admin por erro salva um galpão de OUTRA empresa — sistema usa mesmo assim?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: Admin configura NetAir (empresa A). Por engano, escolhe depósito 42 que pertence a Concorrente Corp (empresa B) na loja.

Hoje o sistema: Sistema salva config. Quando processa pedido, manda pra loja: 'Guardar em depósito 42'. Loja valida: 'Depósito 42 é de empresa B, empresa A não tem permissão'. Retorna erro 403.

Por que importa: Pedido fica preso até alguém perceber. Pode processar de verdade em lugar errado se validação da loja falhar.

  • Ao carregar depósitos, sistema valida: 'Esse depósito pertence a essa empresa?' — A tela mostra só opções corretas. Impossível escolher a errada.
  • A tela lista tudo, o sistema tenta, loja rejeita — Admin só descobre depois.
  • Sem validação, deixa acontecer — Mesma coisa. Erro descoberto durante processamento.

Recomendo: Opção 1: validar na carga de depósitos. A tela mostra só o que é permissível.

src/app/wms/configuracoes/conexoes/page.tsx:693-717 (loadDepositos sem validação de proprietário)

D058Para segurança, a chave de autorização guarda ID da conexão na comunicação — é problema?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: Sistema autoriza na loja. Comunicação inclui identificador da conexão (UUID). Terceiro intercepta a comunicação.

Hoje o sistema: Identificação da autorização = UUID-da-conexao:aleatório. Terceiro vê UUID e deduz qual conexão tá sendo autorizada.

Por que importa: Informação mínima (não é crítica) mas pode ajudar ataque. Se alguém sabe qual conexão você tá autorizando, pode tentar interferir.

  • Identificação = aleatório puro (sem UUID). Sistema registra qual conexão = identificação no banco e busca inverso. — Fora a relação, ninguém sabe qual UUID tá sendo autorizado.
  • Deixar como está — risco baixo — Simples. Mas pequena exposição.
  • Usar padrão moderno de autorização (como PKCE) + identificação aleatória — Mais seguro. Padrão moderno.

Recomendo: Opção 1 ou 3. Opção 1 é mínima, opção 3 é overkill. Comece com opção 1.

src/app/api/wms/tiny/oauth/route.ts:42 (state = connectionId:uuid format)

D059Banco de logs de aviso cresce 500/dia — nunca limpa. Eventualmente fica lento?

🟡 você decideIntegração com a loja (Tiny / marketplace)

Imagina assim: Cada aviso que loja envia é registrado em tabela. 500 avisos/dia × 365 dias = 182.5 mil registros/ano. Sem limpeza.

Hoje o sistema: Tabela cresce indefinidamente. Hoje é rápido porque tem mil registros. Em 5 anos, terá 900 mil.

Por que importa: Tabela grande = consultas lentas = painel demora pra carregar relatório de avisos.

  • Arquivar: deletar automático de registros com mais de 90 dias — Tabela capa em ~90k registros. Consultas rápidas sempre.
  • Partição por data: novo arquivo de dados a cada mês — Mesma coisa, mas mais eficiente no storage.
  • Deixar crescer — Funciona agora. Em 5 anos, relatórios ficam lentos.

Recomendo: Opção 1: implementar rotina automatica que deleta registros > 90 dias. Simples e eficaz.

docs/database-schema.md (webhook logs não mencionam retention)
