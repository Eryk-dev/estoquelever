## Codebase Patterns
- STATUS_SEPARACAO_COLORS, STATUS_SEPARACAO_LABELS, and filter OPTIONS arrays exist in BOTH `pedidos/page.tsx` AND `pedidos/[id]/page.tsx` — update both when adding a new status
- COMPRA_STATUS_COLORS and COMPRA_STATUS_LABELS also exist in `pedidos/[id]/page.tsx` — update when adding a new compra_status
- COMPRA_STATUS_MAP in `separacao-card.tsx` is the separacao module's version of compra status display
- SeparacaoCounts initializers exist in 3 places: `api/separacao/route.ts` (2x: emptyCounts + counts), `separacao/page.tsx` (EMPTY_COUNTS)
- COUNT_STATUSES in `api/separacao/route.ts` maps by array index to countResults — adding a new status requires updating both the array and the index-based counts builder
- Amber color scheme for "pending validation" states: `bg-amber-100 text-amber-800 dark:bg-amber-900 dark:text-amber-300`
- iniciar/route.ts has a BLINDAGEM + DB guard (.eq/.in on status_separacao) — when allowing new statuses, update ALLOWED_STATUSES, toStart filter, AND the DB update guard
- cancelar/route.ts classifies pedidos into 3 return statuses by compra_status priority: oc_pendente → validacao_oc, other compra → aguardando_compra, else → aguardando_separacao
- voltar-etapa/route.ts STATUS_ORDER array determines valid admin move targets — add new statuses in flow order
- OC creation pattern (find-or-create siso_ordens_compra by fornecedor + galpao): used in produto-esgotado/route.ts and validar-oc-item/route.ts — always match by fornecedor + galpao + status='aguardando_compra'
- EventoPedido type in historico-service.ts must include new event types before they can be used in registrarEvento calls
