Produtos que são feitos de componentes (Kits)

Quando você vende um produto que é montado de outros produtos (exemplo: um kit presente com 5 itens). O sistema "desmonta" automaticamente no pedido, aparta o estoque de cada item componente, e depois controla a separação de cada um em vez de tratar como um único pacote.

O que já funciona

  • ✓Quando você muda a composição do kit (adiciona ou tira um componente), os pedidos antigos continuam com a composição antiga e os novos usam a nova — não mexe um no outro.
  • ✓Se o componente sai de estoque entre o momento que o sistema aparta e o momento que o operador separa, o sistema encontra outro local onde tem estoque.
  • ✓Você consegue depois rastrear qual componente veio de um kit — o registro das movimentacoes de estoque marca.
  • ✓Kits podem conter outros kits (um kit dentro de outro) e o sistema desmorona tudo automaticamente para os componentes reais.

Problemas pra resolver · 2

P120Kit criado vazio não funciona

graveCadastros (produtos, prateleiras, fornecedores)

Imagina assim: Operador marca um produto como kit, mas não coloca nenhum componente dentro

Hoje: Quando um pedido chega com esse kit, o sistema aceita, expande para nada, e depois tenta apartar estoque de algo que não existe

Por que importa: Um kit vazio é como pedir uma caixa com 0 itens — o operador pensa que tá tudo ok, mas na hora de separar não tem nada pra guardar e o pedido fica preso

Bloquear na entrada — quando marca kit=verdadeiro, obrigar adicionar pelo menos 1 componente antes de deixar salvar

  • Validar ao criar/editar o kit no cadastro — Impede kit vazio desde o início; mais caro fazer, mas zero pedidos com problema
  • Validar apenas quando o pedido chega (aviso da loja) — Deixa cadastro solto, mas rejeita pedido — operador vê erro, volta atrás
  • Deixar como está — Continua falhando silenciosamente; pedidos e estoque ficam confusos

Recomendo: Fazer bloqueio no cadastro. Se alguém marca kit=verdadeiro, não deixa salvar enquanto tiver 0 componentes.

webhook-processor-wms.ts:222-228

P121Quantidade negativa ou zero em componente do kit

graveCadastros (produtos, prateleiras, fornecedores)

Imagina assim: Operador tenta adicionar um componente com quantidade 0, -1, ou vazio

Hoje: Código tem validação só no servidor e só lança erro (código 500 genérico); a tela não avisa antes de enviar

Por que importa: Um kit com parafuso de -5 unidades não faz sentido; quebra o cálculo de quantos kits estão disponíveis

Bloquear no formulário da tela ANTES de enviar, e manter validação no servidor com mensagem clara

  • Bloquear só na tela (não deixa digitar quantidade ≤0) — Mais rápido, mas se alguém burlar, servidor retorna erro confuso
  • Bloquear na tela E retornar mensagem clara do servidor — Dupla proteção; operador vê aviso legível
  • Deixar como está — Erro 500; operador tira print, manda pra TI, ninguém sabe o que aconteceu

Recomendo: Opção 2 — validar nos dois lugares. Tela avisa ali mesmo; se vier solicitação estranha, servidor devolve código 400 com mensagem tipo 'quantidade deve ser ≥ 1'.

route.ts:72; kits.ts:217-219

D111E se o operador clicar botão Aprovar 2 vezes muito rápido no mesmo pedido com kits?

🟡 você decideEtapas do pedido (separação, embalagem, envio)

Imagina assim: Pedido com kit, botão Aprovar, operador clica 2× em menos de 1 segundo

Hoje o sistema: Sistema checa se já tem reservas; se tem, ignora a 2ª tentativa. Janela de risco: entre ler o pedido e começar a apartar estoque, 2 cliques podem passar.

Por que importa: Se ambos os cliques viram aprovações de verdade, aparelha o mesmo estoque 2 vezes — o pedido usa estoque que não tem, ou o saldo fica negativo.

  • Deixar como está (risco pequeno, <500ms na tela) — Funciona 99% das vezes; se acontecer, descobrimos post-mortem e ajustamos
  • Bloquear no banco de dados com regra rigorosa (tudo-ou-nada) — Garante que nunca duplica, mesmo com operações rodando em paralelo; mais seguro, precisa migração
  • Desabilitar botão após 1º clique — Impede clique duplo na tela; mas se vier de operação interna, não para

Recomendo: Se 99% dos acessos é tela Web (operador), opção 3 é suficiente e rápida. Se tem operação ou integração paralela, fazer opção 2 — adicionar validação no banco de dados para garantir que executa uma vez só.

aprovar/route.ts:428-436

D194Pedido pede componente X solto E pede kit que contém X — como conta?

🟡 você decideCadastros (produtos, prateleiras, fornecedores)

Imagina assim: Pedido: 5× Parafuso + 1× Kit Suporte (que tem 3× Parafusos). Estoque tem 10 parafusos no total.

Hoje o sistema: Sistema soma tudo — 5 diretos + 3 do kit = 8 parafusos apartados. Nenhum aviso de duplicação. Registro mostra que 3 vieram do kit (campo kit_componente=true) mas não bloqueia.

Por que importa: Operador pode pensar que comprou 5+1=6 coisas mas o sistema apartelha 8 parafusos. Estoque confuso. Ou pode ser intencional — precisa saber se permite redundância.

  • Deixar como está (soma tudo; rastreabilidade post-fato) — Devolve quem quer isso. Mais flexível, mas silencioso se foi erro.
  • Avisar quando detecta redundância (parafuso já dentro do kit) — Operador vê alerta, decide se remove o direto ou mantém
  • Bloquear e forçar corrigir (não deixa aprovar se tiver redundância) — Garante integridade; pode impedir pedidos legítimos (ex: preciso mesmo de 8 parafusos)

Recomendo: Conversar com o dono de negócio: componentes dentro de kits podem ser redundantemente solicitados? Se não deve acontecer, ir com opção 2 ou 3. Se pode, opção 1 é ok desde que treine operador.
