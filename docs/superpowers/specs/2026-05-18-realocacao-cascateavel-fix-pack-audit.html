Critical · 5 achados

C1

Frontend envia só itemIds[0] em parcial de realocação agregada

Critical Frontend 1 linha de código

Cenário

Wave consolidou 3 pedidos com o mesmo SKU. Cascade gerou 3 realocações no mesmo destino A-02-3 (uma por pedido_item). UI agrupa visualmente em 1 linha (qty 3). Operador João clica "Parcial → peguei 2, loc zerou".

Comportamento atual

src/app/wms/separacao/checklist/page.tsx:597 — manda { realocacao_id: parcialModal.itemIds[0], ... }. Só o primeiro ID, mesmo o array tendo 3.

Comportamento esperado

Mandar { realocacao_ids: parcialModal.itemIds, ... }. O backend (refatorado no fix do bug 2) já aceita array via parcial/route.ts:82-84.

Fix sugerido

Trocar realocacao_id: itemIds[0] por realocacao_ids: itemIds no body da chamada (linha 597). 1 linha.

Impacto se não fizer

As outras 2 realocs do grupo ficam aguardando_picking apontando pra loc que já teve mov ajuste loc_zerou aplicado (saldo = 0). Cascade nunca dispara pra elas. Pedidos travam em estado inconsistente. Regressão direta do fix anterior — backend foi refatorado pra aceitar array, frontend não foi atualizado.

C2

desfazer-parcial estorna mov_ajuste_loc_zerou_id violando spec

Critical Backend Drift de ledger

Cenário

Operador deu parcial com loc_zerou (pegou 2, sistema dizia 5 → mov ajuste estorna 3). Operador percebe que errou, clica "desfazer parcial".

Comportamento atual

src/app/api/wms/separacao/desfazer-parcial/route.ts:82-88 chama estornarMovimentacao(mov_ajuste_loc_zerou_id). Sistema devolve saldo de 3 que fisicamente não existe.

Comportamento esperado

Spec invariante (docs/superpowers/specs/2026-05-18-realocacao-cascateavel-design.md) e cancelar/route.ts:79-80 dizem: "mov_ajuste_loc_zerou_id NUNCA é estornado por design — reflete descoberta física". Quem zera é uma contagem futura.

Fix sugerido

Remover linhas 82-88 do desfazer-parcial/route.ts. Manter estorno só do mov_saida_id + reset dos campos.

Impacto se não fizer

Cada parcial-desfeito cria saldo fantasma. Próxima wave pega saldo que não existe, dispara nova parcial loc_zerou, sistema gera nova mov ajuste, ciclo repete. Reconciliação cron eventualmente acusa, supervisor manual.

C3

mov_saida_id amarrada só no primeiro beneficiário do wave consolidado

Critical Backend Decisão estrutural

Cenário

Wave consolidou 3 pedidos com mesmo SKU. Operador deu parcial: 1 mov S total qty=5. Os 3 itens ficaram separacao_parcial=true com quantidade_pega proporcional, mas só o item beneficiário tem mov_saida_id setado. Operador agora quer desfazer parcial em um dos itens.

Comportamento atual

parcial/route.ts:358-359 (item) e :809-810 (realoc) — mov_saida_id: ehBeneficiario ? movSaidaId : null. Apenas 1 dos 3 registros ganha o ID. Se o operador desfaz no beneficiário, estorna mov inteira (que cobria os 3) — outros 2 ficam órfãos. Se desfaz no não-beneficiário, mov_saida_id é null, nada é estornado, mas item é resetado.

Comportamento esperado

Desfazer-parcial em qualquer item do wave deve ou (a) estornar proporcional, ou (b) recusar com mensagem clara, ou (c) cada item ter sua própria mov.

Fix sugerido — 3 opções (preciso da sua escolha)

  • (a) Tabela ponte siso_pedido_item_mov_links(pedido_item_id, mov_id, qty). Schema change. Elegante. Desfazer recalcula.
  • (b) Bloquear desfazer em wave. Zero schema change. UX restritiva: operador precisa cancelar wave inteira. Detecta via origem_detalhes.pedido_item_ids.length > 1.
  • (c) 1 mov por pedido_item. Modo realoc gera N movs em vez de 1 consolidada. Sem ambiguidade. Mais inserts no ledger.

Impacto se não fizer

Wave consolidado é um caso comum (mesmo SKU em N pedidos do dia). Cada desfazer cria ou ledger drift ou item órfão. Reconciliação manual frequente.

C4

Sem lock pessimista em siso_pedido_item_realocacoes — race condition

Critical Backend Concorrência

Cenário

Operador A e Operador B bipam a mesma realocação no mesmo wave ao mesmo tempo (ambos clicam "marcar realocação" em janelas de milissegundos).

Comportamento atual

parcial/route.ts:569-597 e marcar-realocacao/route.ts:31-48 fazem SELECT da realoc sem FOR UPDATE. Ambos veem status aguardando_picking, ambos chamam inserirMovimentacao (a RPC interna tem FOR UPDATE em siso_estoque, então os dois rodam sequencial — mas ambos passam). Resultado: 2 movs S no ledger pra 1 realocação.

Comportamento esperado

UPDATE condicional WHERE id = $id AND status = 'aguardando_picking' retornando linhas afetadas. Se 0, abortar 409.

Fix sugerido

Substituir o SELECT-then-UPDATE por UPDATE...RETURNING com filtro condicional. Antes de gerar mov, garantir que o UPDATE pegou a linha.

Impacto se não fizer

Estoque drenado 2x da loc. quantidade_pega do item pai recebe 2x via read-modify-write. mov_saida_id aponta só pra última mov. Em produção com 2 operadores no chão, isso acontece toda semana.

C5

Tabela de realocações fora da publication supabase_realtime

Critical Migration UX cross-operador

Cenário

Operador A e B no mesmo wave. A cria cascade (nova realoc surge) ou marca uma realoc. B deveria ver na UI.

Comportamento atual

Nenhuma migration adiciona siso_pedido_item_realocacoes à publication supabase_realtime. checklist/page.tsx também não tem subscribe nem polling — só invalidateQueries após mutation própria. B só vê mudança ao refresh manual.

Comportamento esperado

Per CLAUDE.md ("Direção Estratégica"): "Toda tabela que afeta operação ao vivo entra na publication". B deveria reagir em <1s.

Fix sugerido

Migration: ALTER PUBLICATION supabase_realtime ADD TABLE siso_pedido_item_realocacoes. Estender use-realtime-separacao pra escutar a tabela.

Impacto se não fizer

Op A marca realoc → Op B vê estado velho → Op B tenta marcar a mesma → 409 (C4) ou pior. Confusão garantida em wave compartilhado.

Important · 11 achados

I1

pendente_realocacao é cidadão de segunda classe em 5 endpoints

Important Backend Fluxo bloqueado

Cenário

Pedido entrou em pendente_realocacao (cascade sem cobertura no galpão). Operador ou admin tenta resgatar.

Comportamento atual

  • iniciar/route.ts:76-89 — status válidos não incluem pendente_realocacao
  • marcar-item/route.ts:59-65 — idem
  • encaminhar/route.ts:131-138 — só aceita aguardando_separacao/em_separacao (caso de uso CENTRAL — encaminhar quando galpão esgota — bloqueado)
  • voltar-etapa/route.ts:19-26 — status fora do STATUS_ORDER
  • produto-esgotado/route.ts:54-65 — fora dos ACTIVE_STATUSES

Comportamento esperado

O design original previa: cascade falhou → modal abre → operador encaminha pra outro galpão ou cria OC. Mas o endpoint encaminhar rejeita o pedido nesse status. Único caminho hoje: desfazer-parcial → fluxo refaz.

Fix sugerido

Adicionar pendente_realocacao em todos os 5 endpoints como status aceito. Em encaminhar, antes do switch de galpão: cancelar realocs aguardando + estornar movs do galpão origem.

Impacto se não fizer

Pedido entra em pendente_realocacao e fica preso. Operador fica chamando supervisor. Em produção, vai ser o ticket #1 da primeira semana.

I2

encaminhar não estorna mov_saida nem cancela realocs do galpão origem

Important Backend

Cenário

Pedido picado parcialmente em CWB (mov S registrada, realocs aguardando). Decisão: encaminhar pra SP refazer.

Comportamento atual

encaminhar/route.ts:190-200 reseta separacao_marcado, quantidade_bipada, bipado_completo, estoque_saida_lancada — mas não toca em quantidade_pega, separacao_parcial, parcial_*, mov_saida_id, mov_ajuste_loc_zerou_id. Estorno via Tiny legado só se estoque_lancado=true. Realocs órfãs no galpão origem.

Comportamento esperado

Encaminhar = "abandono este galpão". Cancela todas realocs aguardando, estorna mov_saida_id, reseta todos os campos parciais.

Fix sugerido

Helper compartilhado resetarEstadoSeparacao(supabase, pedidoIds, usuarioId) chamado também em voltar-etapa, reiniciar, produto-esgotado modo encaminhar.

Impacto se não fizer

Mov fica órfã em CWB; realoc aguardando fica órfã; pedido vai pra SP com separacao_parcial=true causando confusão.

I3

reiniciar/route.ts reseta só separacao_marcado

Important Backend

Cenário

Operador clica "Reiniciar progresso" durante wave em andamento que já tem parcial + cascade.

Comportamento atual

reiniciar/route.ts:82-98 reseta só separacao_marcado + timestamp. Mov S fica no ledger. Realocs picadas continuam picadas. quantidade_pega, separacao_parcial, mov_saida_id persistem.

Comportamento esperado

"Reiniciar progresso" volta ao zero — estornar movs, cancelar realocs aguardando, resetar campos parciais.

Fix sugerido

Mesmo helper compartilhado do I2.

Impacto se não fizer

Item visualmente "não pego" no UI, WMS já fez saída. Operador refaz, mov duplicada, estoque drenado 2x.

I4

concluir-oc não bloqueia realocs pendentes

Important Backend

Cenário

Pedido OC tem item com realoc aguardando_picking (cascade ainda não pega).

Comportamento atual

concluir-oc/route.ts:51, 92-99 só checa separacao_marcado=true. Nunca consulta siso_pedido_item_realocacoes. Pedido vai pra separado com realoc em aberto.

Comportamento esperado

Bloquear se há realoc aguardando_picking em qualquer item do pedido — espelhar o check de concluir/route.ts:59-75.

Fix sugerido

Adicionar a mesma query de bloqueio que existe em concluir/route.ts.

Impacto se não fizer

Pedido OC sai pra embalagem com realoc órfã. Ledger inconsistente.

I5

compras-release cego a mov_saida_id já feitas — double-deduct

Important Backend Drift de estoque

Cenário

Pedido híbrido: alguns itens viraram cascade (parcial + realoc picada — mov S já no ledger), outros viraram OC. OC chega.

Comportamento atual

compras-release.ts:49-67 lê só compra_status e enfileira lancar_estoque cegamente pra todos os itens. Worker legado deduz estoque dos itens cascade pela segunda vez.

Comportamento esperado

Worker honra mov_saida_id já preenchido (skip dedução). Ou release passa flag com itens já lançados.

Fix sugerido

No payload da fila, adicionar itens_ja_lancados: [ids com mov_saida_id] e worker honra.

Impacto se não fizer

Double-deduction. Saldo WMS diverge da realidade. Reconciliação cron eventualmente acusa, mas só depois do dano.

I6

Embalagem usa só quantidade_bipada >= quantidade_pedida

Important Backend RPC Pedido travado

Cenário (A)

Parcial sem cobertura total — qty pega real = 7 de 10. Operador físico só tem 7 peças. Bipou 7. bipado_completo nunca vira true, pedido fica preso em separado sem aviso claro.

Cenário (B)

Operador usa confirmar-item-embalagem (botão +/- manual) e fura — bipou só 7 mas clica +3 sem ter peças. Pedido sai expedido com qty diferente da NF.

Comportamento atual

RPC siso_processar_bip_embalagem e confirmar-item-embalagem/route.ts:86 usam só qty bipada vs pedida. Nunca consulta quantidade_pega ou realocs.

Comportamento esperado

Mostrar no UI: "qty pega real = 7 vs pedida = 10 — fechar parcial?". Bloquear bipar acima da qty pega real.

Fix sugerido

Tela embalagem soma item.quantidade_pega + Σ(realocs.quantidade_pega). RPC valida teto quantidade_pega em vez de quantidade_pedida quando item tem separacao_parcial=true.

Impacto se não fizer

Pedido sem cobertura total trava silencioso, ou expede com qty errada → NF Tiny incompatível com saída real.

I7

DELETE /realocacao/[id] não cancela filhas em chain

Important Backend

Cenário

Realoc raiz (A-02-3) gerou cascade pra filha (A-04-1). Operador cancela a raiz.

Comportamento atual

realocacao/[id]/route.ts:39-42 só seta status='cancelado' na raiz. Filha com parent_realocacao_id = raiz continua aguardando_picking.

Comportamento esperado

Cancelar toda a chain via parent_realocacao_id. Se alguma filha já foi picada (mov gerada), retornar 409 sugerindo desfazer wave inteiro.

Fix sugerido

Query recursiva (CTE) ou loop iterativo cancelando descendentes em aguardando_picking. 409 se algum descendente em picado*.

Impacto se não fizer

Chain órfã. Supervisor vê "raiz cancelada → filha aguardando" e fica confuso. Pode bipar filha que não devia.

I8

Cascade em wave multi-empresa usa só o primeiro pedido residual

Important Backend

Cenário

Wave consolida pedidos de NetAir e NetParts (mesma SKU, mesmo galpão CWB, mesmo grupo). Parcial dispara cascade.

Comportamento atual

parcial/route.ts:884-922 usa empresaOrigemPrimResid = pedidos[0].empresa_origem_id para resolverProdutoWms, resolverRealocacao e locOriginal. Items do pedido 2..N: is_emprestimo flag pode estar errado, loc original do pedido 2..N pode ser re-sugerida no cascade.

Comportamento esperado

Computar individualmente por residual, ou agrupar por empresa_origem antes do cascade.

Fix sugerido

Loop: agrupar residuais por empresa_origem_id → cascade por grupo. Ou (simpler) bloquear wave consolidado cross-empresa por enquanto.

Impacto se não fizer

Em wave cross-empresa, alguns itens podem ter is_emprestimo errado. Hoje raro porque waves geralmente são single-empresa, mas o dia que cair vai gerar drift de saldo devedor.

I9

Read-modify-write em quantidade_pega do item pai sem lock

Important Backend Race condition

Cenário

Wave + algo paralelo (worker / outro endpoint mexendo no mesmo item).

Comportamento atual

parcial/route.ts:828-837 e marcar-realocacao/route.ts:124-128 — lê item.quantidade_pega, soma, escreve. Cache local atualizado em memória pra iterações.

Comportamento esperado

UPDATE atômico numérico: SET quantidade_pega = COALESCE(quantidade_pega, 0) + $delta.

Fix sugerido

RPC wms_acumular_qty_pega(item_id, delta) que faz UPDATE atômico RETURNING. Substituir os 2 call-sites.

Impacto se não fizer

Em produção com paralelismo, quantidade_pega pode ficar abaixo do real. Concluir aceita pedido com qty < pedida sem saber.

I10

produto-esgotado modo OC ignora quantidade_pega parcial

Important Backend Compras infla

Cenário

Item já tem parcial (quantidade_pega=3 de 10). Operador clica "Esgotado → criar OC".

Comportamento atual

produto-esgotado/route.ts:257 seta compra_quantidade_solicitada = item.quantidade_pedida (10 inteiro). Solicita OC pelos 10 — duplicando os 3 que já saíram.

Comportamento esperado

Solicitar pelo residual: quantidade_pedida - quantidade_pega - Σ realocs.quantidade_pega.

Fix sugerido

Computar residual antes de setar compra_quantidade_solicitada.

Impacto se não fizer

Compras infla. Fornecedor entrega a maior. Reverter manual.

I11

Auth ausente em 4 endpoints destrutivos

Important Backend Auditoria

Cenário

Qualquer requisição com payload válido reseta state sem autenticação.

Comportamento atual

produto-esgotado/route.ts:23-50, reiniciar/route.ts, concluir/route.ts, checklist-items/route.ts:34-66 — não chamam getSessionUser. Eventos sem usuarioId.

Comportamento esperado

Todo endpoint mutador exige sessão.

Fix sugerido

const session = await getSessionUser(req); if (!session) return 401 no início de cada um.

Impacto se não fizer

Vetor de ataque interno (qualquer um na rede). Auditoria perdida — não sabe quem cancelou/reiniciou.
