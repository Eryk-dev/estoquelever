Snapshot inicial + Reconciliação

Como o sistema é "ligado" pela primeira vez carregando estoque do Tiny — e como ele se auto-cura quando algo divergir.

A ideia em 2 frases

Snapshot inicial: quando o WMS sobe pela primeira vez, ele precisa importar o estoque atual do Tiny. Esse processo lê os saldos de cada produto+empresa+galpão no Tiny e cria a primeira entrada no histórico do WMS. É a "fundação" do sistema.


Reconciliação: ao longo do tempo, o resumo de estoque exibido nas telas pode divergir do histórico (por bug raro, intervenção manual no banco, restore mal feito). A reconciliação detecta a divergência e reconstrói o resumo somando o histórico inteiro.

Snapshot inicial — o "go live"

Quando uma empresa começa a usar o WMS, o estoque dela já existe — em vários galpões, várias posições. O sistema precisa "saber" desse estoque antes de processar qualquer venda nova.

Como funciona o snapshot — passo a passo

  1. Admin chama o processo (pela tela ou endpoint).
  2. Pode rodar em modo "dryRun": só simula, mostra o que seria feito sem fazer.
  3. Sistema lista todos os produtos cadastrados.
  4. Pra cada par produto+empresa, consulta o Tiny perguntando "qual o saldo agora?".
  5. Tiny responde com saldos por depósito (galpão).
  6. Sistema verifica se já existe movimentação no WMS pra esse par. Se sim, pula (idempotente). Se não, cria uma entrada inicial.
  7. A entrada é gravada com categoria "Inventário inicial" — fácil de identificar e separar de operações normais.

Idempotência

O snapshot pode ser rodado várias vezes sem efeito colateral. Se já foi rodado antes, ele só processa o que ainda não tinha sido importado (novos produtos cadastrados, novas empresas). Isso é importante porque a migração é gradual: começa com 1 empresa, depois adiciona outra, etc.

Reconciliação — saúde contínua

Depois que o sistema está rodando, há uma rotina de checagem que compara:

Fonte da verdadeResumo na tela
Soma de todas as movimentações do históricoTabela cached que é atualizada a cada movimentação

Em condições normais, os dois batem. Quando não batem, é alerta — e o sistema sabe reconstruir o resumo do zero.

Cenário 1 — Snapshot inicial

A situação

WMS recém implantado. NetAir tem ~5.000 produtos cadastrados no Tiny, distribuídos em 2 galpões. Total de saldos no Tiny: ~50.000 unidades. Vamos importar tudo.

O que o admin faz

  1. Acessa o endpoint de snapshot (administrativo).
  2. Confirma a empresa de destino (NetAir).
  3. Sistema começa a processar.
  4. Loop: pra cada produto cadastrado, consulta Tiny, cria entradas iniciais.
  5. Processo demora minutos (depende do volume).
  6. Ao final, mostra resumo: "X produtos processados, Y entradas criadas".

Resultado

Histórico depois do snapshot
QuantidadeCategoria
~5.000 linhasInventário inicial
Resultado: WMS passa a "ver" o estoque inteiro da NetAir. A partir desse momento, novas vendas vão funcionar normalmente (descontando do saldo importado). Foi o "go live".
Pra quê serve a categoria "Inventário inicial"? Pra distinguir movimentações de carga inicial das operacionais. Relatórios "vendas dos últimos 30 dias" precisam excluir essa categoria pra não inflar. Auditoria entende imediatamente que aquela linha não é compra nem venda.

Cenário 2 — Snapshot em dryRun

A situação

Antes de rodar o snapshot de verdade, admin quer ver o que seria feito. Usa modo dryRun.

Como funciona

  1. Admin chama o endpoint com flag dryRun=true.
  2. Sistema executa todo o processo, menos a gravação.
  3. Retorna um relatório:
    • Produtos que seriam importados (e a quantidade de cada)
    • Produtos que seriam pulados (já existem)
    • Erros que foram encontrados (peça não encontrada no Tiny, dados inválidos, etc)

O admin revisa

Relatório dryRun
StatusQuantidade
Criaria nova entrada4.823
Pularia (já existe)12
Erro (peça não encontrada no Tiny)5

Admin investiga as 5 com erro. Pode ser:

  • Peça desativada no Tiny mas ainda cadastrada no WMS (decisão: ignorar)
  • SKU duplicado no Tiny (corrigir lá antes)
  • Falha de rede momentânea (retry resolve)
Resultado: admin tem ciência completa do que vai acontecer. Pode resolver problemas antes de rodar o snapshot de verdade. Confiança no processo de carga.

Cenário 3 — Snapshot repetido

A situação

2 meses depois do go-live da NetAir, vamos adicionar a NetParts no WMS. Rodamos o snapshot de novo, agora pra NetParts.

O que acontece

  1. Sistema processa cada par produto+empresa.
  2. Pares NetAir já têm histórico — sistema pula todos.
  3. Pares NetParts são novos — sistema cria entradas iniciais.
  4. Saldos atuais da NetAir (do dia-a-dia) ficam intocados. Só NetParts ganha entradas iniciais.
Relatório
EmpresaCriadosPulados
NetAir05.012
NetParts3.8470
Resultado: NetParts agora também tem estoque no WMS. NetAir permanece como estava — sem dobra de saldos. Idempotência funcionando como esperado.
E se quiser re-importar saldos da NetAir? Tipo, achou que tinha bug no snapshot original? Tem que primeiro limpar as entradas iniciais existentes (operação manual de administração) e rodar de novo. Pra evitar bagunça acidental, o sistema nunca sobrescreve sozinho.

Cenário 4 — Reconciliação detecta

A situação

Toda madrugada, um robô do sistema roda a reconciliação no modo "só detectar":

  1. Pra cada posição (peça+empresa+galpão+localização), soma o histórico inteiro.
  2. Compara com o resumo cached.
  3. Se igual, ok.
  4. Se diferente, registra alerta com detalhes:
    • Qual posição
    • Saldo "histórico" (somado)
    • Saldo "cached" (na tabela de resumo)
    • Diferença

Exemplo de saída

Divergências detectadas
PosiçãoHistórico somaResumo cachedDivergência
NetAir / CWB / CWB-A1-01 / PEC-1004240+2
NetParts / SP / SP-B1-02 / PEC-5011516−1
Resultado: 2 posições divergentes detectadas. Sistema só alerta — não corrige automaticamente. O admin (ou time técnico) investiga o que aconteceu. Pode ser bug recente, intervenção manual, etc.
Por que não corrigir automaticamente? Porque divergência indica que algo está errado no fluxo. Corrigir sem investigar mascara o problema. Melhor alertar, descobrir a causa raiz, corrigir o fluxo, e só depois aplicar a correção.

Cenário 5 — Reconciliação com auto-fix

A situação

Time técnico investigou as divergências do cenário 4 — concluiu que foi um bug antigo já corrigido. Agora vai aplicar a correção rodando reconciliação em modo "auto-fix".

Como funciona

  1. Admin chama o endpoint com flag fix=true.
  2. Sistema detecta divergências (igual ao cenário 4).
  3. Pra cada uma, reconstrói o resumo somando o histórico inteiro daquela posição.
  4. Atualiza o cache com o valor correto.
  5. Loga aviso com o que foi corrigido.

Antes e depois

Antes do auto-fix
PosiçãoCacheHistórico
NetAir / CWB / CWB-A1-01 / PEC-1004042
Depois
PosiçãoCacheHistórico
NetAir / CWB / CWB-A1-01 / PEC-10042 ✓42
Resultado: resumo está alinhado com a fonte da verdade (histórico). O bug que tinha causado a divergência foi corrigido antes — agora não vai voltar a divergir. O histórico nunca foi tocado — ele é imutável. Só o resumo é reconstruído.

Por que confiar no histórico e não no cache?

Porque o histórico é gravado uma vez e nunca mais alterado. É imutável. O cache é uma otimização (pra não ter que somar tudo a cada leitura). Se cache e histórico discordam, o histórico ganha — sempre.

Periodicidade ideal:
  • Detecção (sem fix): diária. Alerta se houver divergência.
  • Auto-fix: mensal ou sob demanda. Só após investigar a causa.
