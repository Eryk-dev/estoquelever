Transferência de estoque entre galpões

Quando você envia estoque de um galpão pra outro: origem separa a mercadoria (a quantidade sai de lá), destino recebe em uma prateleira (a quantidade chega). Os dois podem desfazer até 7 dias depois.

O que já funciona

  • ✓Criar uma transferência com zero estoque ou quantidade parcial funciona
  • ✓Quando dois operadores tentam receber ao mesmo tempo, só um consegue (o outro vê a mensagem de que já está sendo feito)
  • ✓Desfazer o recebimento funciona mesmo 5 dias depois
  • ✓Se você cancela uma transferência que já foi recebida, o sistema rejeita (não deixa confundir a ordem)

Problemas pra resolver · 3

P062Dois operadores tentam receber a mesma transferência ao mesmo tempo — um fica com estoque perdido

graveEtapas do pedido (separação, embalagem, envio)

Imagina assim: Transferência saiu do galpão A com 3 caixas. Operador João começa a guardar a 1ª caixa (abre o formulário, escolhe onde botar). Operador Maria clica para cancelar a transferência inteira.

Hoje: Maria consegue cancelar e desfaz as 2 caixas que já foram guardadas. João consegue guardar a 1ª caixa mesmo depois. Resultado: a transferência fica marcada como cancelada, mas a 1ª caixa está lá na prateleira sem ninguém saber que existe. Fica órfã no sistema.

Por que importa: Você pensa que cancelou a transferência toda, mas parte dela foi recebida escondido. Quando vier um pedido normal, o estoque dessa caixa órfã não aparece. Causa quebra de cabeça em auditorias.

Quem tem direito de cancelar uma transferência que está sendo recebida naquele momento? Só o operador que está recebendo? Ou gerente pode parar qualquer hora?

  • Só quem está recebendo consegue cancelar a transferência — Mais seguro. Se João está recebendo, Maria não consegue cancelar. Mas João pode ficar preso se tela dele cair.
  • Gerente (role especial) consegue cancelar mesmo que alguém esteja recebendo — Mais flexível, mas precisa de outro sistema pra 'liberar' o operador preso se tela dele cair.

Recomendo: Opção 1: configure permissão pra só quem está mexendo conseguir parar. Mas adicione um timeout automático — se o operador cair de internet, após 30 minutos libera o lock automaticamente.

P063Cancelamento de transferência falha no meio — fica meia desfeita e prende o operador seguinte

graveEtapas do pedido (separação, embalagem, envio)

Imagina assim: Transferência em recebimento. A 1ª caixa já foi guardada. Sistema tenta desfazer essa 1ª caixa mas a prateleira onde ela está foi deletada (ou está indisponível). Cancelamento bate em erro.

Hoje: Transferência fica meia cancelada. Algumas caixas foram desfeitas, outras não. Se a prateleira desapareceu, a 1ª caixa fica órfã lá dentro. Operador seguinte que tenta receber: sistema diz 'já tem alguém recebendo' mesmo que não tenha. Precisa de admin para limpar tudo via comando de banco de dados.

Por que importa: Você tenta cancelar mas o sistema trava. A transferência inteira perde a rastreabilidade. Estoque fica partida entre recebida (meia) e não recebida (meia).

Quando cancelamento bater em erro no meio, o que fazer? Continuar ignorando esse erro (marcar cancelado mesmo incompleto)? Ou reverter tudo e deixar a transferência como era antes?

  • Ignorar erro e marcar cancelado de qualquer jeito (o que faz hoje) — Rápido, mas deixa dados inconsistentes. Auditoria consegue rastrear, mas confuso.
  • Se um erro acontece, desfaz tudo que foi desfeito até agora e deixa a transferência como estava — Mais limpo. Mas operador precisa ver qual foi o erro exato pra resolver (ex: prateleira foi deletada, então recrie a prateleira e tente de novo).

Recomendo: Opção 2: se um erro acontece, desfaz tudo que foi desfeito até agora. E mostre a mensagem de erro específica pro operador (ex: 'Prateleira X foi deletada — entre em contato com gerência'). Assim o sistema fica limpo e sabe-se exatamente o que foi errado.

P162Operador digita 12.5 unidades em vez de número inteiro — o sistema aceita e depois quebra

médiaRecebimento e guarda de mercadoria

Imagina assim: Operador está criando uma transferência de 12.5 unidades de um produto. Digita 12.5 no campo de quantidade.

Hoje: Campo aceita o número quebrado. Sistema cria a movimentação com 12.5 unidades. Saldo do estoque vira 12.5. Quando depois for preciso faturar ou separar pro pedido, esses outros sistemas esperam número inteiro e quebram ou geram erro estranho.

Por que importa: Você vende em unidades inteiras, mas estoque fica com número quebrado. Depois quando vai faturar ou separar, conta não fecha. Ou pior: alguém ve 12.5 e arredonda errado (12 ou 13) — estoque não bate mais.

Campo de quantidade deve permitir casas decimais (pra produtos a granel ou tecido) ou só inteiros?

  • Só inteiros — sistema rejeita se digitar 12.5 — Mais seguro pro seu negócio. Operador recebe erro claro: 'Digite um número inteiro'. Simples.
  • Permite decimais (como hoje) — pra produto a granel — Funciona pra produtos especiais. Mas nota fiscal e picking precisam lidar com isso. Mais complexo.

Recomendo: Opção 1: rejeite números quebrados. Se você vende algum produto a granel (quilo, metro), configure esse produto específico pra aceitar decimais — o resto é inteiro.

Decisões pra você tomar · 2

D103Se operador perde internet e fica 'travado' dentro de um recebimento, o sistema deveria liberar sozinho após quanto tempo?

🟡 você decideEtapas do pedido (separação, embalagem, envio)

Imagina assim: Operador João está recebendo uma transferência. Tela dele trava. Sistema marca 'João está recebendo'. Operador Maria chega 1 hora depois e tenta receber — sistema barra ela.

Hoje o sistema: Sistema não libera automaticamente. Fica travado pra sempre até admin limpar via banco de dados.

Por que importa: Você pode ficar sem conseguir receber mercadoria por horas porque um operador caiu de internet. Produtividade cai, galpão trava.

  • Liberar automaticamente após 15 minutos — Operador cai, volta pra trabalhar em 15 min — sistema já liberou. Rápido. Risco: se operador só saiu 5 min pra beber água, volta e acha que alguém mexeu.
  • Liberar automaticamente após 1 hora — Mais seguro (operador realmente caiu). Mas 1 hora é muito tempo — galpão fica travado.
  • Sem liberar automático; operador clica 'liberar meu lock' quando volta — Mais controle, mas precisa treinar operador e ele pode esquecer.

Recomendo: Opção 1: 15 minutos. Se operador sair pra beber água, volta e vê que foi liberado — recomeça rápido. Se realmente caiu, galpão fica só 15 min parado.

D104Quando operador clica 'Receber' mas falha (ex: erro de banco de dados), quem é responsável por limpar o travamento?

🟡 você decideEtapas do pedido (separação, embalagem, envio)

Imagina assim: Operador João reivindicou o direito de receber. Começou a guardar a 1ª caixa. Na 2ª caixa, banco de dados falha (ex: prateleira foi deletada). Sistema não consegue completar.

Hoje o sistema: Sistema tenta limpar sozinho (best-effort) — se conseguir, limpa. Se falhar também, fica preso. João fica marcado como 'ainda recebendo'. Só admin consegue limpar via SQL.

Por que importa: Se banco falha, operador fica preso. Não consegue tentar de novo. Precisa de admin manualmente mexer no banco para liberar. Operação fica muito dependente de admin.

  • Sempre desfaz tudo que foi feito e libera o travamento — João cai, Maria consegue tentar receber de novo. Automático, operador não precisa fazer nada. Limpo.
  • Deixa como está (best-effort) — sistema tenta limpar, mas se falhar, fica travado — Hoje. Admin precisa intervir. Mais trabalho, menos automático.

Recomendo: Opção 1: sempre desfaz tudo que foi feito. Se erro acontece, volta ao início, libera o travamento e mostra pro operador qual foi o problema específico (ex: 'Prateleira foi deletada'). Assim ninguém fica travado.
