Roles & Permissões

Admin configura pelo sistema quem pode ver e fazer o quê — sem precisar mexer em código.

1. Resumo

Hoje, cada vez que um colaborador novo precisa de um perfil de acesso diferente — um "meio-comprador-meio-operador", ou um conferente que só faz inventário — é preciso pedir pra equipe técnica mexer no sistema e fazer um deploy. Com esta feature, o admin abre uma tela, marca caixinhas, e pronto: novo perfil criado e atribuído a quem precisar. O Eryk (admin) vira o dono da matriz de acesso.

Pra que serve
Dar autonomia pro admin pra criar novos perfis de acesso e ajustar o que cada perfil pode ver/fazer, sem depender de programador.

2. Fluxo principal

Existem dois fluxos que se complementam: o do admin configurando e o do colaborador usando. O sistema serve de ponte: o que o admin marca, o colaborador passa a ver (ou deixa de ver) na próxima vez que entrar.

3. Exemplo passo-a-passo

Vamos seguir um caso real: o Eryk precisa criar um perfil "Conferente" pro João, que vai ajudar só no inventário.

Cenário
São 14h32 do dia 21/05/2026. O Eryk (admin) acabou de contratar o João pra fazer cycle count nas próximas semanas. O João não pode ver vendas, nem compras, nem editar produtos — só fazer inventário. Hoje o sistema só tem o perfil "Operador" (que vê quase tudo) ou "Admin" (que vê tudo). Nenhum desses serve.
Eryk abre o painel de Roles

Entra em Configurações → Roles & Permissões. A tela mostra 6 cards: Admin, Operador, Operador CWB, Operador SP, Comprador, Vendedor. Cada um com um cadeado (são roles do sistema, não dá pra apagar) e a contagem "X permissões · Y usuários".

Eryk clica em "+ Nova role"

Abre uma tela limpa. Eryk digita: código conferente, nome Conferente, descrição "Cycle count, sem acesso comercial". Clica em Criar.

Eryk marca as permissões certas

A tela mostra todos os módulos do sistema: Vendas, Visibilidade, Operações, Inventário, Insights, Relatórios, Cadastros, Sistema — cada um expandido com caixinhas de cada permissão. Eryk marca apenas Ver sessões e Contar (handheld) dentro de Inventário. Deixa tudo o resto desmarcado.

Eryk salva as permissões

Clica em "Salvar permissões". Toast verde: "Permissões salvas". Volta na lista de roles — agora aparece "Conferente · 2 permissões · 0 usuários".

Eryk vai na ficha do João

Em Configurações → Usuários, clica no João (que hoje é "Operador CWB"). Na seção "Roles" tem uma lista com checkboxes: Admin, Operador, Operador CWB (marcada), Operador SP, Comprador, Vendedor, Conferente.

Eryk troca a role do João

Desmarca "Operador CWB" e marca "Conferente". Clica em Salvar. Toast verde. A ficha agora mostra "Roles: Conferente".

João sai e entra de novo

São 15h05. João estava com o sistema aberto numa aba antiga ainda como "Operador CWB". Ele faz logout, digita o PIN e entra de novo.

O menu lateral do João muda

Antes ele via 7 grupos: Vendas, Visibilidade, Operações, Inventário, Insights, Relatórios, Cadastros. Agora só vê 1 grupo: Inventário, com 2 sub-itens: Sessões e Métricas. A tela inicial dele já abre direto no Inventário.

João tenta entrar numa tela proibida pela URL

Por curiosidade, João digita na barra de endereço a URL de "Compras". O sistema responde com uma mensagem clara: "Sem acesso a esta tela." Mesmo sabendo o endereço, ele não consegue ver os dados.

Semanas depois, o cycle count termina

O contrato do João acaba. Eryk volta na ficha dele e desmarca "Conferente". Como ficaria sem nenhuma role, Eryk marca "Operador CWB" ou simplesmente desativa o João.

Eryk decide se mantém a role "Conferente"

A role fica disponível pra reuso futuro. Se Eryk quiser limpar, vai em Configurações → Roles → Conferente → "Deletar role". Como tem 0 usuários atribuídos, o sistema permite. Toast: "Role deletada."

4. Estados de uma role

Toda role no sistema está em um destes 4 estados:

Status Significado Como entra Como sai
Sistema · Ativa Role padrão criada na fundação do sistema (Admin, Operador, Comprador, Vendedor, etc). Tem um cadeado, não pode ser deletada nem ter o código mudado, mas o admin pode editar nome, descrição e — exceto pra Admin — também as permissões. Já nasce com o sistema. Não dá pra criar mais roles de sistema pela tela. Não sai. É permanente.
Customizada · Ativa Role criada pelo admin (ex: "Conferente", "Supervisor Picking"). Pode ser editada à vontade, atribuída a usuários, ou deletada se ninguém estiver usando. Admin cria pelo botão "+ Nova role" na tela de Roles. Admin clica em "Deletar role" (botão só aparece se zero usuários têm a role).
Customizada · Inativa Role criada mas desligada temporariamente. Usuários que tinham essa role mantêm o vínculo, mas as permissões dela não contam mais — é como se eles não tivessem essa role. Não aparece em listas pra atribuir. Admin desmarca a caixinha "Ativa" na tela da role. Admin marca "Ativa" de novo, ou deleta a role.
Admin Caso especial da role Admin: sempre tem TODAS as permissões marcadas, sempre fica ativa, sempre tem pelo menos 1 usuário. O sistema impede qualquer ação que pudesse "fechar a porta da casa". Já nasce com o sistema. Não sai. Garante que sempre exista um admin no sistema.

5. Cenários alternativos

O que acontece quando alguma coisa fora do roteiro feliz acontece:

Colaborador entra numa tela que vê, mas não pode agir nela
Situação: João tem a role "Conferente" — pode ver sessões de inventário e contar no handheld, mas não pode criar nem aprovar sessão (isso é só de supervisor). João abre a tela "Sessões de Inventário".
O que o sistema faz: Mostra a lista de sessões abertas (João tem permissão de ver), mas esconde o botão "Nova sessão" no canto superior. Dentro de cada sessão, "Aprovar" e "Aplicar" também não aparecem pra ele. O que ele pode fazer (puxar próxima loc, bipar produtos, finalizar contagem) continua visível e funcional.
O usuário vê: Uma tela útil mas focada — sem botões que dariam erro se clicados. Se ele de alguma forma chegasse a disparar a ação (via URL direta ou dev tools), o sistema bloquearia no servidor com "Acesso negado", mas no uso normal isso nunca acontece — porque o botão simplesmente não está lá.
Admin tenta deletar a role "Admin"
Situação: Eryk vai em Configurações → Roles → Admin, procura o botão "Deletar".
O que o sistema faz: Não mostra o botão. A role Admin é de sistema, tem um cadeado e a opção de deletar simplesmente não existe nessa tela.
O usuário vê: Apenas os campos de nome/descrição editáveis. As permissões aparecem todas marcadas em cinza claro (não-clicáveis), com a frase "A role admin sempre tem todas as permissões."
Admin tenta tirar a role "Admin" do único admin do sistema
Situação: Eryk é o único admin. Por engano, vai na própria ficha e desmarca a caixinha "Admin", marca "Operador" e tenta salvar.
O que o sistema faz: Bloqueia a operação. Como ninguém mais tem a role Admin, ele não pode se rebaixar — senão ninguém mais conseguiria mexer em roles, criar usuários ou alterar conexões.
O usuário vê: Toast vermelho: "Sistema precisa de pelo menos 1 admin." A mudança não é salva, a ficha do Eryk continua como Admin.
Admin tenta deletar role que tem usuários atribuídos
Situação: Eryk criou "Conferente" e atribuiu pra João, Maria e Pedro. Algum tempo depois, decide deletar essa role.
O que o sistema faz: Verifica se algum dos 3 ficaria sem nenhuma role caso ela fosse removida. Se sim, bloqueia.
O usuário vê: Toast vermelho explicando: "Usuários ficariam sem nenhuma role — atribua outra role antes de deletar." Eryk vai na ficha de cada um, atribui outra role (ex: "Operador"), e tenta deletar de novo — agora funciona.
Colaborador é cadastrado mas ninguém atribui role ainda
Situação: Eryk cadastra uma nova vendedora, Carla, mas esquece de marcar uma role pra ela. Carla recebe o PIN e tenta entrar.
O que o sistema faz: Aceita o login (PIN está certo), mas como Carla não tem nenhuma role, ela não tem nenhuma permissão.
O usuário vê: Carla loga, mas a barra lateral fica vazia. A tela inicial mostra: "Usuário sem acesso configurado — contate o administrador." Carla avisa o Eryk, ele atribui a role "Vendedor" e ela faz logout/login pra liberar.
Admin desativa uma role com usuários ativos
Situação: A operação de inventário sazonal terminou. Eryk não quer deletar a role "Conferente" (vai usar de novo no próximo ciclo), mas quer suspender o acesso dos 3 conferentes temporariamente. Em vez de mexer em 3 fichas, desmarca a caixinha "Ativa" na role.
O que o sistema faz: A role fica inativa. As atribuições continuam no sistema, mas as permissões dela não contam mais ao calcular o que cada usuário pode fazer.
O usuário vê: João, Maria e Pedro, no próximo login, abrem o sistema e a barra lateral está vazia (eles só tinham "Conferente"). Quando Eryk reativa a role, o acesso volta no próximo login deles.
Admin muda a role enquanto o colaborador está logado
Situação: João está separando pedidos. Eryk muda a role do João de "Operador" pra "Comprador" porque a equipe foi remanejada.
O que o sistema faz: A mudança vale a partir da próxima ação do João. Cada vez que ele clica em algo, o sistema confere a role atual.
O usuário vê: João tenta bipar mais um item — o sistema responde "Sem acesso". Ele estranha, sai e entra de novo, e agora vê só os menus de Compras. (Em algumas telas que dependem de dados antigos do navegador, ele pode precisar atualizar a página primeiro — F5 resolve.)
Permissão antiga sobra no sistema depois que a feature foi removida
Situação: No futuro, a equipe técnica retira a tela "Insights Financeiros" do sistema. A permissão "Ver insights financeiros" deixou de existir no código, mas a role "Comprador" ainda tem essa permissão marcada na base do sistema.
O que o sistema faz: Ignora a permissão obsoleta silenciosamente — não existe mais nenhuma tela ou ação que peça por ela. Na tela de Roles, aparece um aviso amarelo: "1 permissão obsoleta — clique pra remover."
O usuário vê: Eryk vê o aviso na próxima vez que abrir a role Comprador. Clica pra remover, a base é limpa, sumo do aviso. Operação cosmética — não afeta o acesso de ninguém.
Admin esquece de salvar e fecha a aba
Situação: Eryk marca 12 caixinhas de permissão na role "Supervisor Separação", mas é interrompido por uma ligação e fecha a aba sem clicar em Salvar.
O que o sistema faz: Nada — as mudanças não foram persistidas. Próximo admin que abrir a role vê as permissões antigas.
O usuário vê: Quando Eryk volta, abre a role de novo e nota que as caixinhas voltaram ao estado anterior. (Não há aviso de "alterações não salvas" — pode ser melhoria futura.)
