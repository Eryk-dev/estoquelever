# WMS 6 — Cutover Big Bang pra Produção Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Particularidade:** este plano é primariamente um **runbook operacional** (cutover de produção), não um plano de feature. Várias tasks são operações de infraestrutura (`Files: N/A`) que não produzem código. Os critérios TDD/commit-frequent da skill se aplicam só às tasks que criam scripts (Task 4); nas demais, "verificação" significa observar logs/saídas em vez de rodar tests.

**Goal:** Migrar a Fase 0 do WMS — validada em staging através dos planos 1-5 — para produção via **big bang num fim de semana**. Aplicar as 5 migrations em prod, fazer snapshot fresco do Tiny no instante do cutover, fazer deploy do código WMS, validar com smoke tests, reativar webhook do Tiny e iniciar monitoramento intensivo. Sem dual-write, sem transição gradual: vira a chave de uma vez. Plano de rollback documentado caso algo crítico falhe na janela.

**Architecture:** Cutover atômico com janela de manutenção de ~5h efetivas (22h-3h) dentro de buffer total de 14h. Sequência rígida: pausa webhook Tiny → pg_dump full → aplica 5 migrations no project_id de produção (NÃO branch staging) → snapshot fresco do Tiny direto na `siso_estoque` de produção → deploy via Vercel → smoke tests automatizado e manual → reativa webhook → monitoramento intensivo de 4h com user online. Rollback baseado em restore do dump enquanto webhook estiver pausado (cenário A); pós-reativação, hotfix é preferido sobre rollback (cenário B).

**Tech Stack:** mesmo dos planos 1-5 (Next.js 16, Supabase Postgres 15, Vercel, Tiny ERP API v3, PrintNote). Ferramentas adicionais de cutover: `pg_dump`/`pg_restore` (PostgreSQL CLI), Supabase MCP (`apply_migration`, `list_branches`), painel Vercel (Environment Variables + manual deploys), painel Tiny ERP (config de webhooks por empresa).

**Spec de referência:** [docs/superpowers/specs/2026-05-07-wms-design.md](../specs/2026-05-07-wms-design.md) — seção "Promoção pra prod" + decisões aplicadas em [`wms-decisoes-do-user.md`](wms-decisoes-do-user.md) seção I.

**Pré-requisitos (TODOS obrigatórios antes de iniciar):**
- ✅ Planos 1, 2, 3, 4, 5 concluídos em staging
- ✅ Time treinado pessoalmente (decisão A do user) — cada operador foi orientado nas telas WMS staging
- ✅ User validou pessoalmente os cenários funcionais de aceitação dos 5 planos
- ✅ Backup automatizado do Supabase de prod ativo (Pro tier — backups diários)
- ✅ Operadores avisados da janela com pelo menos 72h de antecedência
- ✅ Tiny ERP: webhook config em prod **acessível** (você precisa conseguir desativar/reativar manualmente)
- ✅ PrintNode: API key configurada e funcionando em prod (não muda no cutover)

**Decisões já tomadas (decisão I em `wms-decisoes-do-user.md`):**
- **Estilo:** big bang num fim de semana
- **Dual-write paralelo:** NÃO (substitui a "Fase 1" mencionada nos planos 1-5)
- **Por galpão:** NÃO — CWB e SP cortam juntos
- **Janela:** sábado 22h → domingo 12h (14h de buffer)
- **Rollback aceito:** sim, caso falha crítica na janela

- [ ] **Step 2: Backup manual via pg_dump**

Tamanho esperado: ~50-200 MB pro volume atual. Verificar checksum:

```bash

```

## Rollback playbook

> **Quando rollback é viável:** entre Task 6 (pausa webhook) e Task 12 (reativação webhook). Nessa janela, voltar atrás é "limpo".
>
> **Quando rollback fica caro:** depois da Task 12, pedidos reais já estão sendo processados no schema novo. Voltar significa migrar dados de volta manualmente. Geralmente preferir hotfix em vez de rollback.

### Cenário A: Rollback antes da reativação do webhook (Task 12)

- [ ] **A1.** Confirmar webhook ainda pausado no Tiny.
- [ ] **A2.** Restaurar dump (Task 7):
  ```bash
  # CUIDADO: isso APAGA o estado atual do banco prod
  pg_restore --clean --if-exists --no-owner --no-privileges \
    -d "$PROD_DB_URL" \
    /tmp/siso-prod-CUTOVER-*.dump
  ```
- [ ] **A3.** Reativar webhook Tiny (mesma config de antes).
- [ ] **A4.** Validar que sistema antigo voltou a funcionar (pedido teste).
- [ ] **A5.** Anotar incidente em `wms-cutover-log.md` com causa-raiz.
- [ ] **A6.** Marcar próximo FDS como nova janela de cutover após corrigir.

**Tempo esperado:** 15-30 min.

### Cenário B: Rollback após reativação (Task 12+)

Caro. Antes de rollback, considerar:
- **Opção 1:** Hotfix do bug em prod (deploy via Vercel) sem mexer em banco.
- **Opção 2:** Pause WMS feature flag (`WMS_ENABLED=false`) e voltar pra fluxo legado nas telas que ainda existem. Banco fica novo, mas sistema usa só campos antigos.
- **Opção 3:** Rollback completo (raro). Requer migrar de volta os pedidos novos manualmente.

**Decisão:** se cenário B for necessário, parar e chamar consultoria técnica externa antes de executar. Não fazer sozinho na pressa.

## Cenários funcionais de aceitação

Mesmos cenários dos planos 1-5, executados em prod:

1. **Pedido `propria` auto-aprovado:** webhook NetAir CWB com SKU em estoque → auto-aprova → entra em separação → operador completa → embalado → expedido. Saldo correto em todas as etapas.

2. **Pedido `transferencia`:** webhook NetParts SP com SKU só em CWB → entra na fila pra decisão humana → user aprova como transferência → workflow completo.

3. **Pedido `oc`:** webhook com SKU sem estoque em nenhum galpão → vai pra `/compras` → comprador marca como comprado → recebe → libera pra separação.

4. **Inventário cycle count:** sessão criada com defaults (blind, 2%, 1000) bate com decisão C. Operador conta. Divergência registrada. Aprovação acima de R$ 1000 trava no painel admin.

5. **Empréstimo:** SKU sem estoque na empresa origem mas presente em empresa do mesmo grupo → roteamento sugere empréstimo → contabilidade reflete custo da credora.

6. **Devolução:** webhook NF devolução simulado → aparece em `/wms/devolucoes` → user classifica → mov no ledger → custo médio recalculado.

7. **Reconciliação:** desativar webhook por 10 min, criar pedido no Tiny, reativar webhook, rodar reconciliação → pedido aparece no SISO.
